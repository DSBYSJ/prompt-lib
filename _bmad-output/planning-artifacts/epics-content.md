## 为什么这个 Epic 只有一条 Story

内容扩充本身不需要四阶段文档 —— 给 BMAD 每一步都配套全套产物，是形式主义。
但它有**两个真实风险**，值得单独成篇：

1. **数量涨了质量掉**：为了凑数塞进"看起来像提示词"的段落，用户搜到一条没用的，比搜不到更伤；
2. **数据错误没人拦**：`prompts.ts` 现在是纯手写数组，id 重复、`{{` 少一半、category 写错，
   都不会有任何报错——只会在运行时表现为"这条点开是空白"。

所以本期真正交付的是：**12 条新内容 + 一道能拦住数据错误的数据完整性测试**。

## 目标

| # | 判据 |
|---|---|
| 1 | 总数 **≥36**，且每个分类 **≥5** |
| 2 | 新增条目必须写清「什么时候用」，且互不重复（不是同一条换个说法） |
| 3 | 每条至少含 1 个变量或明确的输入位置（否则无法填） |
| 4 | 新增数据完整性测试：id 唯一、必填非空、分类合法、花括号成对、标签非空 |
| 5 | 既有 52 条单测仍绿；构建通过 |

## 非目标

| 不做 | 原因 |
|---|---|
| 新增分类（如"生活""法律"） | 5 类已够用；分类多了侧栏变噪音，且要动导航与配色 |
| 让用户远程投稿 | 个人备案不得有 UGC，见 Epic 1 brief 第五节 |
| 把数据搬到 JSON + 远程加载 | 见 architecture ADR-3，代价已在 README 写明 |
